# v3.8.51-quattro.1 release notes (draft)

**Status:** draft; no tag has been created.

- **Upstream base:** OmniRoute `v3.8.51`, base commit
  `2acbfc6fa6ef13e55552ce5bc3de45cbf2e535be`
- **Fork release:** `v3.8.51-quattro.1`

## Fork-specific changes

- capability-aware auto-routing with fail-closed execution requirements;
- practical model input limits and explicit minimum-context routing gates;
- versioned feature negotiation and sanitized candidate snapshot APIs;
- optional bounded external routing requirements and ordered preferences;
- eligibility-first cheapest-capable selection;
- bounded combo retry/fallback lifecycle;
- quota, cooldown, and rate-limit-aware fallback;
- sanitized candidate rejection reasons;
- Gemini replayed tool-alias, queue timeout, and disabled vision-provider fixes.

## Compatibility

Standard Chat Completions, Responses, model, and auto-route requests do not require enhanced
metadata. The `routing` extension is optional and removed before provider translation.

## Known limitations

- candidate pricing is `unknown` when no trustworthy local catalog value exists;
- latency class is `unknown` until bounded runtime telemetry is available;
- the conservative execution registry treats unverified providers as chat-only;
- this release remains based on the recorded 3.8.51 base and is not an upstream release.

## Quattro integration

See [docs/integrations/quattro.md](../integrations/quattro.md). Quattro can use standard OmniRoute;
this fork is recommended for full candidate observability and adaptive preference routing.

## Security notes

Candidate snapshots omit account/connection identifiers, credentials, OAuth state, cookies, raw
provider errors, and private configuration. Routing metadata is schema-validated, bounded, treated
as untrusted, and never forwarded to providers.
